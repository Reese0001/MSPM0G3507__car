# 电机 UART 间歇超时修复设计

## 问题

小车运行或转弯后停止，D1 常亮、D2 继续闪烁。D2 表明主循环仍在运行；
D1 表明控制或电机安全故障已经锁存。静态检查发现电机 UART 的发送等待存在
确定性的时序缺陷：

- UART 波特率为 115200，一个 8N1 字节需要约 86.8 微秒；
- 现有代码用 1000 次 CPU 循环作为超时，在 80 MHz 下处于约 75 微秒量级；
- 每发送一个字节前都等待 UART 完全空闲，使这个边界超时在每个字节重复发生；
- 一旦发送返回失败，`motor_safety` 会锁存故障、点亮 D1 并发送零速命令。

## 方案比较

1. 增大循环次数：改动最小，但时间随编译优化和主频变化，不可靠。
2. 保留逐字节 `BUSY` 等待，改为硬件微秒超时：时间可靠，但会继续把 UART
   串行化，发送效率低。
3. 每字节仅等待 TX FIFO 可写，整帧末尾再等待 UART 空闲，所有等待使用现有
   1 MHz 时间基准：符合 TI UART 的发送模型，时间确定，改动仍局限于一个模块。

采用方案 3。

## 设计

只修改 `modules/motor/bsp_motor_usart.c` 和对应测试：

- 每个字节发送前轮询 TX FIFO 是否已满；
- 使用 `BSP_Time_GetUs()` 计算无符号时间差，避免依赖 CPU 循环次数；
- 整帧写入后等待 `DL_UART_isBusy()` 清零，确认帧发送完成；
- 任一阶段超过固定微秒期限时，保持现有行为：重启 UART 并返回 `false`；
- 不修改速度、转角算法、软启动、200 ms 看门狗、换向停顿或故障锁存策略；
- 不修改 SysConfig 生成文件。

超时期限应覆盖最长速度帧在 115200 波特率下的发送时间，并保留调度和中断余量。
首版使用一个短而明确的模块常量，不引入新抽象或依赖。

## 验证

1. 先增加宿主测试，证明等待由微秒时间决定，而不是循环次数。
2. 验证 TX FIFO 满时等待、超时返回失败、整帧完成返回成功。
3. 运行现有全部宿主测试。
4. 使用 TI Arm Clang 编译全部活动源文件并完成链接。
5. 重新生成 UniFlash 可用的 HEX/TXT，并核对两者地址和数据一致。

## 实车安全

首次烧录测试时轮子架空，保留软启动、看门狗、换向停顿和零速急停。该修复不提高
PWM 或目标速度，只消除 UART 软件超时的不确定性。
